# 字段、时间与判定规则

本文件是执行口径。`cases.md` 保存历史材料，有未修正的叙述和机器推断；两者冲突时采用本文件的校正，并在分析中说明实际证据。所有项目阈值均为本案例库适用条件下的经验，不是全行业标准。

## 1. 字段与机型基线


## 2. 时间和计算

- PM:INFO 标称固定1分钟一次，这是用户对旧项目的最终确认；案例6的“高频打印”已被案例14更正。
- `I>20.230`、`I>21.300` 等内部计数前缀**不可相减当秒或分钟**。
- 优先使用与记录明确关联的绝对时间/epoch。壁钟校时、跨日跨年、时区、重启复位和格式混杂时分段处理，不能默认拼接连续时间；文件名时间不是每条日志的时间锚点。
- 仅在确认采样连续、无缺失重复且未跨启动段时，N条记录首尾可估算为 `(N−1)×周期`。否则只报告行数和趋势，不伪造精确速率。采样估算必须标注假设。
- 充电、补电、满电平台、SOC回弹/跳变、重启、长时间日志空洞分别切段。对有效放电段计算，不能跨充电直接以首尾电量差代表耗电。

公式（ΔSOC用百分点数，如21，不是0.21）：

```text
放电速率(%/h) = (起始SOC − 结束SOC) / 时长(h)
估算平均电流(mA) = 容量(mAh) × ΔSOC / 100 / 时长(h)
线性外推满电天数 = 100 / 放电速率 / 24
充电倍率(C) = 等效充电电流(mA) / 容量(mAh)
```

230mAh时，1%/h约2.3mA；31→10%若为30分钟，则42%/h、96.6mA。平均电流单位用 **mA**；电荷量用mAh；没有电压依据不报告mW。SOC推算电流不等于实测电流，尤其是电量计异常、老化、极端温度和充电跳变时。线性续航外推不是承诺。

## 3. R1–R9判定

### R1：VBUS输入电压与充电上下文

按用户2026-10-27新确认，旧称“f6”的第6字段实际为VBUS电压，单位mV；正常充电一般需要4.5V以上。应解释其物理状态，而不是只输出“字段正常/越界”。

- 非充电上下文中接近0V的VBUS（旧案例0–100mV经验带）是未接充电电源的线索，不作为低充电电压故障。
- 已确认插入充电器、期望正常充电时，VBUS低于约4500mV，或持续不稳定，可作为充电输入异常线索；结合插拔、接触、线缆、电源与充电阶段分析。单条切换瞬态不能直接确定器件损坏或漏电。
- 旧4500–5500mV是案例库的充电经验带，并不是本次用户确认的绝对完整正常规格。高于5500mV需结合具体充电电源/硬件规格核验，不能仅凭旧带宽自动断言硬件故障。
- 历史案例7把44xx称正常，与一般4.5V以上充电条件不符；现在按“低于一般充电输入基线、需结合上下文核验”处理，不静默下调基线。案例中“缺口带”对应VBUS中间电压，不是一个物理语义未知的独立故障码。
- VBUS达到正常充电电压，只说明充电输入条件的一部分，不能排除持续耗电、传感器漏电或电池异常；**VBUS电压不能用来计算电池充电C倍率**，C倍率仍来自电流/容量或标明假设的SOC变化率。

### R2：POR及重启前后

`reset_reason=0` 是旧项目的异常线索，结合当时电量、正常上电/断电/维修背景和时间线分析。电池耗尽或真实上电也可能出现POR，不能仅据POR确定漏电。3是软件重启，6是关机原因，均不等同POR。

**项目排查前提（用户确认，2026-10-24）**：一般认为重启可以消除软件导致的异常耗电。确认重启发生在异常放电窗口之前，且重启后耗电仍高于本项目正常场景基线时，默认按“软件因素已通过重启排查，优先判断硬件漏电”处理。只有日志或复现提供明确的软件异常证据，才重新考虑软件原因；不要把没有证据的软件可能性列为常规阻碍。

确认“重启后仍异常”不强制要求重启前完整窗口；但声称“重启前后速率一致/未改善”时，需要前后有效窗口且场景、温度与配置可比。仅看到文件中有重启记录，尚未确认其与异常窗口先后关系时，不能使用这项排查前提。

### R3：未佩戴高耗电

用明确的未佩戴区间关联耗电，不用全文件未佩戴多数替代异常窗口的佩戴状态。确认无充电，并对照同机型同配置的静置基线。若估算电流接近/超过经确认的对应场景整机上限，强化硬件漏电判断；基线适用性不明时只报告高耗电待核验。

### R4：掉电与升温联动

同一放电窗口持续快速掉电，同时温度快速上升，是案例库最主要的硬件漏电/故障组合信号。展示至少首尾及中间点，检查充电、运动负载、环境升温和SOC跳变等影响。

案例17：行204915→207640，31→10%，33→54℃，31条PM记录，f6=f7=0；用户判定硬件漏电。**f6正常、未检出POR不否定该模式。** 不要求附加传感器失败才可作项目硬件判断。

45℃、50℃分别是历史异常/极端发热提示值；并非跨机型通用硬阈值，≤36℃也不能据此判正常。f5来源未知时，不能用nst11x失败直接证明或否定f5的真实性。

### R5：持续、均匀的异常耗电

先确认“异常”：同场景正常机、已知待机规格或可信整机负载上限。再比较多个放电段、按小时窗口及重启前后。低SOC量化误差较大，优先看较长窗口；未建立统计阈值，不编造方差门槛。

案例7/11/13约2.6–4mA是历史经验样本，**不是统一漏电阈值**。恒定耗电和干净日志支持项目判断，但也可能来自持续软件负载。单个外设最大电流不等于整机所有负载总上限。与上限比较时说明基线与配置。

案例18新增项目上下文：Helio Strap无GPS、屏幕等重度耗电外设；软件重启后仍有64→38%、约10.6h的长放电段（约2.45%/h，230mAh口径约5.64mA）。用户判定硬件漏电。不能用带屏/GPS手表的负载解释该手环，但也不新增5.64mA通用阈值。用户进一步确认，一般认为重启可消除本项目软件导致的异常耗电；本例按“重启后仍异常”优先判断硬件漏电，不把未经日志支持的软件猜测作为必要保留项。该例未建立重启前后速率对比，不能宣称前后速率相同。

**案例20补充：软件最重负载上限（用户确认，2026-10-24）**。本手环无GPS、屏幕等重度耗电外设，MCU不休眠时待机整机约6mA；用户确认本项目软件引起的最重耗电也约6mA。在有效放电段、容量/时间口径有依据且配置适用时，持续估算电流明确超过6mA，可按项目经验判断存在硬件漏电；多次重启后仍异常进一步互证。不必要求同时出现升温、POR或f6越界，也不因泛化的“其他软件负载可能性”弱化用户已确认的项目上限。对其他机型仍需单独确认整机上限；接近6mA且估算误差可能改变是否超限时说明边界。

本例98→88%/178min≈3.37%/h；按250mAh约8.43mA，按230mAh约7.75mA，均超过6mA。8.43mA反算的250mAh不是直接确认的机型容量，不把MILI各机型容量统一改成250mAh。跨1970年复位时间的区间不计算全局速率。

### R6：外设/传感器失败

**输出要求（用户明确要求，2026-10-27）**：以后只要检出这类失败，就必须在分析结果中单独明确指出，并列代表性原文，不能只用“传感器异常”或“双地址失败”笼统带过。展示原日志行号或时间；重复错误可汇总次数/启动段，不必贴全部重复行。

必须按实际命中解释以下链条：

```text
nst11x EC=4 addr 0x4b id fail
nst11x EC=1 nst11x_ic_init fail
Thermo EC=3 thermo_init fail
```

分别表示0x4b器件ID读取失败、nst11x芯片初始化失败、Thermo温度功能整体初始化失败。发现0x4a失败也明确列出地址；若整体初始化成功，则明确写“局部器件失败，但thermo_init success”，不改写成整体失败。统计是日志条数还是独立启动段要区分，核对后续是否恢复。将该证据与掉电/升温时序关联，不能不加验证直接认定某个器件就是漏电根因。

关键词：`nst11x ... i2c read/write fail`、`nst11x_ic_init fail`、`Thermo ... thermo_init fail`。以原文为准，注意`nst11x`不是OCR的`nstllx`。

旧项目地址映射：0x4a=env、0x4b=skin，需结合驱动和机型验证。仅0x4a失败而`thermo_init success`，证据弱于双地址失败且整体初始化失败；多次启动重复失败增强持续故障信号。初始化失败可以来自器件、总线、供电、配置或软件，**不单独证明器件损坏，更不证明其导致漏电**。结合R4及硬件复测定位因果。

`SFTL sftl_idle_task:sftl_idle_gc/wl done` 在历史项目中是例行维护，不因E>前缀单独记作故障；其他SFTL错误不能一概忽略。

### R7：充电SOC跳变

**正常充电基线更正（用户确认，2026-10-24）**：产品一般1分钟上涨1个百分点，0→100%约1.5小时。前者对应100分钟充满、0.60C；后者对应90分钟充满、约0.67C，两者都是近似经验，不要求每分钟严格匀速。正常平均等效基线统一写约0.6–0.7C；230mAh按0.60–0.67C细算约138–153mA。旧0.2–0.5C、46–115mA、2–5h满充口径已废止，不再用于本项目判定。

C倍率可由百分比速率直接换算：`C = 每分钟上涨百分点 × 0.6`。单格1%/min约0.6C，持续2%/min约1.2C，持续3%/min约1.8C。SOC推算倍率、全程平均和实测恒流电流是不同口径：恒流段可以高于全程平均，不将0.7C当硬性损坏阈值。判断充电段偏快时，优先与正常机相同阶段比较，再与放电/重启证据互证。

根据插拔和充电上下文、VBUS电压与充电阶段辅助确认充电段，分别检查恒流、恒压/末端和满充维持；阶段3暂按用户推测的恒流理解，不强制所有机型充电阶段必须为3，也不擅自锁定其他阶段枚举。

旧项目持续约3%/min为异常经验，230mAh可推算414mA、1.8C，**这是SOC等效值，不能证明实际充入414mA**。考虑电池有效容量变小、电量估算/标定异常及充电电路问题；仅凭SOC跳变不能自动确认硬件损坏，需正常机/实测/维修互证。保留用户已给出的硬件损坏结论及其来源。

**案例19补充（用户确认，2026-10-24）**：不把3%/min当成R7唯一触发条件。SOC速率换算为 `等效倍率(C)=ΔSOC百分点/100/时长h`；1C对应约1.67%/min。先看持续窗口，结合正常机/项目约0.6–0.7C的平均等效基线，持续接近或超过1C也要报告为充电异常线索。单分钟+3%可能受SOC取整影响，需观察跨分钟趋势。

本例37→58%/约12min≈1.05C，另外52→70%/约11min≈0.98C、45→82%/约23min≈0.97C；用户将这些充电行为作为硬件异常判断依据。与重启后约7mA的持续异常放电互证，增强硬件异常/漏电判断。不能因f6未越界、温度未剧升、未达到持续3%/min而漏查充电倍率；也不能仅凭接近1C的SOC推算值确认实际超1C电流或具体硬件损坏。

案例16“20→79%、59分钟、3%/min”互相矛盾：59个百分点若按3%/min约19.7分钟，若59分钟则约1%/min。该例未经本次原日志复核，不能用错误时长定阈值，也不能将截图序列省略号当完整采样。

### R8：脱离充电后电压快速回落，疑似电池异常

用户在案例21给出的新判定分支：拔掉充电器后，f3电池电压快速回落并伴随SOC下降，优先考虑**疑似电池损坏/电池异常**。这与持续漏电分支分别评估，不把“电池异常”直接改写为“已确认漏电”。

- 关联充电结束、f6/f7状态切换和用户拔出描述，记录最后充电样本、第一条离充电样本及随后数分钟电压/SOC/温度。采样间的确切拔出时刻未知时不伪造。
- 案例21：离充电后约3分钟，f3从43025降至40811，SOC99→95%；约6分钟到91%，温度25–27℃；之后电压回升至41144/41180。用户结论为“疑似电池坏了”，不据此确定内阻增大、容量衰减或某个器件损坏。
- 充电停止后的正常电压松弛也会回落；用同机型、同充电阶段和可比负载的正常机曲线区分，必要时测负载压降/内阻/容量。当前没有统一mV/min或SOC跌幅硬阈值，不用单条回落直接确诊。
- f3物理语义已在本日志族获得用户确认，数值缩放尚未锁定；输出原始值或明确标注换算假设。不要仅因像4万就直接除以10000报告伏特。
- 电池状态/SOC估算异常可能使标称容量×SOC变化无法代表真实耗电；命中该模式时，先报告电压和SOC事实，不能仅据推算电流超过6mA就确定漏电。仍可结合强发热、真实电流及维修证据判断两种问题是否并存。

### R9：佩戴关联异常，疑似健康sensor漏电

案例22新增用户经验：同一设备非佩戴时耗电低（约每天3%），佩戴时异常升高（约5.3mA），重启后仍如此，优先考虑**疑似健康sensor漏电**或相关供电路径异常。不能只查全文件平均耗电而漏掉状态相关差异。

- 对齐佩戴、非佩戴与充放电时间线，分别计算较长纯放电段，记录混合状态和运动配置。区分窗口主体状态与100%单一状态；尽量找状态切换前后和重复切换佐证。
- 验证重启前后先后关系，不把横跨重启的大窗口全称为重启后。用户已确认本项目通常通过重启排查软件因素；无需无证据重复泛化软件猜测。
- 比较的是相对该场景正常功耗的异常，**低于6mA并不排除漏电**。6mA软件最重负载上限不是正常佩戴基线。也不以21倍差异、5.3mA或每天3%设跨产品硬阈值。
- 正常佩戴也会开启健康测量，单纯佩戴比未佩戴耗电不是器件故障充分条件。结合项目异常判断、重启和同配置正常机/健康功能开关试验，保留“疑似”的置信程度。
- “健康sensor”尚不指向具体器件；没有证据时不自动写为温度、PPG、心率或其他特定sensor损坏。可建议通过分路供电、电流或功能开关进一步定位。
- 案例22用户非佩戴口径48→43%/46.38h，本次原日志匹配约45.45h，均约每天3%；佩戴99→21%/34.12h≈2.29%/h≈5.26mA（230mAh）。保留时间差异而不伪造一致。

**案例23强化（2026-10-26，用户提供怀疑方向）**：佩戴98→20%/约49h，230mAh约3.66mA、满电线性约2.62天；摘下后SOC18%维持约24h。用户怀疑PPG或其相关电路漏电，可把该方向列为R9具体候选，但不直接确认PPG损坏，不推广到所有佩戴关联异常。无需PPG fail、强发热或f6越界才可保留这一怀疑。

R9中的“重启后仍异常”是增强信号，不是怀疑成立的必备条件；本例重启发生在摘下后，不能反向证明重启排除了此前佩戴耗电的软件因素。约24h显示同一整数SOC，不代表真实零耗电或恰好消耗1%；没有连续佩戴日志时区分用户描述与原日志逐分钟可核验范围。

## 4. 合并证据

不设置机械评分或规则命中数门槛。R4强联动、R1持续异常、R2背景异常和R6重复失败可互证，但可能共享同一根因，不能当作独立概率相乘。R3/R5需场景基线；R7需确认实际充电行为。

用户明确给出结论时记录为用户结论；机器核验支持哪些事实就写哪些。推算异常较强时可判项目硬件漏电/故障，但具体器件、电容漏电或短路需直接证据。未命中规则不代表正常，只有异常案例库也不足以证明特异性。

案例21的R8为独立电池异常分支：维持“疑似”强度，避免将电压松弛/SOC回落与漏电机械合并。
